## Поддерживаемая платформа

Windows 10 2004 / build 19041 и новее, Windows 11; Intel/AMD x64. Установщик не принимает Windows 7/8, 32-битную Windows и ARM. Рекомендуются 8 ГБ ОЗУ и 4 ГБ свободного места на время установки; это ориентир, а не измерение минимальной конфигурации. Локальные команды работают без сети, нейросетевые подключения необязательны. Ollama и Claude Code устанавливаются отдельно, если выбран соответствующий способ подключения.

## Установка и профиль

- Inno Setup 6.7.4, русский и английский мастер; установка для текущего пользователя, `PrivilegesRequired=lowest`.
- По умолчанию `%LOCALAPPDATA%\Programs\JARVIS`; ярлык «Пуск», необязательный ярлык рабочего стола и запись в установленных приложениях.
- Маркер `jarvis.install.json` отделяет установленную версию от разработки. В установленной версии данные — `%LOCALAPPDATA%\JARVIS\data`, временные файлы — `%LOCALAPPDATA%\JARVIS\work`. Ресурсы и среда запуска читаются из папки установки.
- Данные не входят в установщик и не удаляются деинсталлятором. Автозапуск и микрофон по умолчанию выключены. При удалении убирается только запись автозапуска, указывающая на удаляемый EXE.
- Перед установкой/обновлением полностью выйти из JARVIS. Установщик проверяет mutex; принудительно завершать чужой рабочий процесс он не должен.
- Переход с старого прототипа пока без автоматической миграции: исходная папка `data` остаётся на месте. Отдельный перенос допустим на том же Windows-профиле с резервной копией; сессии DPAPI не предназначены для переноса другому пользователю.

## Сборка

На подготовленном компьютере: `scripts/build-installer.ps1`. Компилятор `.tools/inno/ISCC.exe` можно заменить параметром `-InnoCompiler`. Полный payload каждый раз создаётся в новой папке `artifacts/installer-build-<timestamp>`. Скрипт проверяет тесты, публикует self-contained win-x64, формирует комплект по разрешённому списку, запускает проверку моделей/синтеза, затем компилирует EXE и пишет SHA-256. Результаты не коммитятся в Git.

`prepare_installer.py` не копирует `data`, `.venv`, `.git` или рабочие каталоги. Python устанавливается в отдельный runtime из зафиксированных пакетов с проверкой хешей; `._pth` изолирует его от системного Python. Модели проверяются по `models.lock.json`. MSVC DLL поставляются рядом с Python. Лицензии, карточки моделей и архивы исходников отдельных зависимостей включены в `third-party`. `payload-sha256.json` проверяется скриптом `verify_installer.py`.

## Проверки и ограничения

Автотесты 0.11.0: 311 Core + 13 Windows + 33 Python; ruff. Автономный `Jarvis.exe --check-installation <report.json>` не включает микрофон и воспроизведение: проверяет загрузку всех моделей и синтез фразы. Проверка выполнялась с неверными внешними PYTHONHOME/PYTHONPATH/DOTNET_ROOT; загружена именно включённая .NET-среда.

Проверка установщика использует отдельный AppId, без пользовательских ярлыков и без конфликта с запущенным прототипом. Установка, повторная установка и удаление проверяются в отдельной папке с пробелом и кириллицей. Это не равно тесту на чистой Windows без установленного ПО: такую проверку ещё нужно провести на другом ПК.

Установщик не подписан сертификатом издателя. Автоматическое обновление, автоматическая миграция прототипа, восстановление предыдущей версии, подпись и отдельная ARM-сборка остаются будущими задачами.

Кириллица в пути: Vosk требовал UTF-8 ACP. В манифест только встроенного `python.exe` добавлен `activeCodePage=UTF-8`; системная локаль не меняется. Повторная загрузка моделей и синтез успешно проверены в папке `Установка JARVIS`. Основание: [Microsoft — UTF-8 code page per process](https://learn.microsoft.com/en-us/windows/apps/design/globalizing/use-utf8-code-page). Для self-contained EXE в `AppHostDotNetSearch` обязательно оставлять `AppLocal`.

## Обновление и восстановление · 0.11.0

По запросу пользователя сборки выполняются локально, GitHub CI временно не запускать. У установленной версии сохраняется прежний AppId. Установщик читает только свою запись установки текущего пользователя: прежнюю версию и папку.

- Нет записи: обычная первая установка.
- Версия старее: «Обновление JARVIS», показ обеих версий и прежней папки, кнопка «Обновить».
- Версия совпадает: «Восстановление JARVIS», кнопка «Восстановить»; файлы приложения переписываются, отсутствующие возвращаются.
- Установлена более новая версия: понижение блокируется с объяснением.

При обновлении/восстановлении страницы выбора папки и ярлыков пропускаются; сохраняются прежние параметры. Пользователь полностью закрывает JARVIS перед запуском. Принудительного завершения процесса нет. Профиль в `%LOCALAPPDATA%\JARVIS` не входит в payload и не удаляется. Восстановление касается файлов приложения, не сбрасывает пользовательскую конфигурацию. Удаление доступно стандартно через «Установленные приложения» Windows.

Тест на отдельном AppId и небольшой контрольной поставке подтвердил первую установку, обновление 0.10 → 0.11 без повторного указания папки, восстановление повреждённого EXE, запрет понижения, удаление и сохранность пользовательского файла. Логи: `work/maintenance-*.log`, сценарий: `work/test-maintenance.ps1`.

Финальная поставка 0.11.0 подготовлена локально из новой self-contained публикации и неизменённых runtime/models/speech/third-party предыдущего полного payload. Перед повторным использованием проверены все 5928 файлов по манифесту 0.10.0; новая поставка имеет собственный манифест и маркер 0.11.0. Обычный `build-installer.ps1` также обновлён на 0.11.0. Отдельная проверка `--check-installation` новой поставки загрузила модели и синтезировала ответ при намеренно неверных внешних переменных среды, без микрофона и воспроизведения. Данные пользователя не использовались.

Официальные механизмы: [сохранение идентичности установки](https://jrsoftware.org/ishelp/topic_setup_appid.htm), [сравнение версий](https://jrsoftware.org/ishelp/topic_isxfunc_comparepackedversion.htm).

## План релизов и обновлений через GitHub

Добавлено по явному запросу пользователя 8 ноября 2026 года. Выполнять после восстановления доступности GitHub CI; до этого сохраняется локальная сборка. Ни релизный workflow, ни проверка обновлений в приложении сейчас не реализованы.

1. Настроить релизную сборку Windows через GitHub Actions: тесты, сборка автономного установщика, проверка комплекта и обновления предыдущей версии. Версия приложения, тег и версия установщика должны совпадать. Публиковать только успешно проверенную сборку соответствующего коммита.
2. Публиковать установщик, контрольную сумму и описание изменений в GitHub Releases репозитория `german-webdev/jarvis`. Личные профили, настройки и авторизацию в релиз не включать.
3. Добавить в JARVIS проверку новых опубликованных стабильных релизов: ручную кнопку «Проверить обновления» и настраиваемую автоматическую проверку. Показывать текущую и доступную версии, изменения и размер загрузки. Черновики и предварительные релизы по умолчанию не предлагать.
4. Загружать выбранный релиз из GitHub с отображением прогресса и возможностью отмены; проверять целостность перед запуском установщика. Недоступность сети или GitHub не должна мешать локальным функциям JARVIS.
5. Предлагать установку загруженной версии из приложения: корректно завершать JARVIS, запускать существующий механизм обновления поверх прежней установки, сохранять настройки, каталоги и подключения, затем давать возможность снова запустить приложение. Подтвердить успешность по фактически установленной версии. Фоновая проверка сама по себе не означает неожиданное закрытие приложения или установку без решения пользователя.
6. Проверить весь путь: опубликованный релиз → обнаружение в старой версии → загрузка → обновление → запуск новой версии; отдельно проверить отмену, оборванную загрузку, повреждённый файл, отсутствие сети, повторную проверку актуальной версии и сохранность профиля.

Способ подписи/проверки подлинности, периодичность фоновых проверок и восстановление после неудачного обновления уточнить при реализации. Сам запрос на добавление этого плана не снимает текущий запрет на запуск GitHub CI.
